# Documentation: `KannalaBrandt8.h`

## High-Level Overview
The `KannalaBrandt8.h` file declares a specific implementation of the `GeometricCamera` interface. 
It mathematically models extreme wide-angle and fisheye lenses using the **Kannala-Brandt** model (specifically, the 8-parameter variant used by OpenCV).
Unlike a standard pinhole camera where light travels in a perfectly straight line, a fisheye lens bends light dramatically at the edges to capture a wider field of view. The Kannala-Brandt model accurately approximates this bending using a polynomial expansion of the incident ray angle.
This class is crucial for robotics utilizing omnidirectional cameras (like the Intel RealSense T265).

**Primary Dependencies:**
- `GeometricCamera.h` (The base abstract class).
- `TwoViewReconstruction.h` (Used for monocular map initialization).

## Block-by-Block Breakdown

### 1. Class Definition and Serialization

```cpp
class KannalaBrandt8 final : public GeometricCamera {
    template<class Archive>
    void serialize(Archive& ar, const unsigned int version)
```
**Explanation:** 
- `final`: This keyword prevents any other class from inheriting from `KannalaBrandt8`. The mathematics are highly specific and should not be modified by subclassing.
- **Serialization:** It serializes the base class (`GeometricCamera`, which contains the actual 8 parameters) and its specific `precision` variable.

### 2. Constructors and Parameters

```cpp
KannalaBrandt8() : precision(1e-6)
KannalaBrandt8(const std::vector<float> _vParameters)
```
**Explanation:** 
- The constructors initialize the camera. 
- `mvParameters` expects exactly 8 values in a very specific order: 
  - `[f_x, f_y, c_x, c_y, k_0, k_1, k_2, k_3]`
  - `f_x, f_y`: Focal lengths.
  - `c_x, c_y`: The principal point (optical center) of the image.
  - `k_0, ..., k_3`: The four radial distortion coefficients defining the polynomial curve of the fisheye lens.
- `mnType = CAM_FISHEYE`: Tells the rest of the SLAM system to treat this object as a fisheye camera (triggering different code paths in Epipolar searches).

### 3. Overridden Interface Functions

```cpp
cv::Point2f project(const cv::Point3f &p3D);
cv::Point3f unproject(const cv::Point2f &p2D);
cv::Mat projectJac(const cv::Point3f &p3D);
```
**Explanation:** 
- These functions override the pure virtual functions in `GeometricCamera`.
- **`project`**: Applies the Kannala-Brandt distortion equations to map a 3D ray into 2D distorted pixels.
- **`unproject`**: Because the Kannala-Brandt equations are highly nonlinear polynomials, they cannot be perfectly inverted analytically. `unproject` uses an iterative numerical solver (like Newton-Raphson) to find the 3D ray. This is why the `precision(1e-6)` variable exists—it defines the stopping criteria for this iterative numerical solver.
- **`projectJac`**: Computes the highly complex analytical derivatives of the Kannala-Brandt equations with respect to the 3D point $X, Y, Z$, outputting a $2 \times 3$ matrix used by g2o.

### 4. Fisheye-Specific Epipolar Geometry

```cpp
bool epipolarConstrain(GeometricCamera* pCamera2, const cv::KeyPoint& kp1, const cv::KeyPoint& kp2, ...);
float TriangulateMatches(...);
bool matchAndtriangulate(...);
```
**Explanation:** 
- **The Epipolar Curve:** In standard pinhole cameras, given a point in image 1, the search space in image 2 is a straight line (the Epipolar Line). In a fisheye camera, this search space is a complex 2D curve.
- `epipolarConstrain` evaluates whether a putative match `kp2` actually lies on the epipolar curve generated by `kp1` within a certain error margin (`unc`).
- `matchAndtriangulate` wraps the robust triangulation logic necessary to handle rays coming from extreme angles.

### 5. Multi-Camera Overlap Support

```cpp
std::vector<int> mvLappingArea;
```
**Explanation:** 
- "Lapping Area" (Overlapping area). 
- When using a dual-fisheye setup (two cameras pointed in opposite directions, like a 360 camera), their fields of view overlap at the seams.
- `mvLappingArea` stores the bounding pixel coordinates where this physical overlap occurs, enabling the tracking thread to recognize when a feature is visible in *both* cameras simultaneously.
